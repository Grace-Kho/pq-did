# R0-DESIGN-REVIEW-1 — decision after the CredValid po2-17 result

19 September 2026. **Keep the current RISC Zero CPU proving configuration paused.**
The measured execution and the checked proof-cost projection do not support spending
the last proof attempt. Neither relation-preserving optimisation has an evidenced
path to the unchanged application targets, even together. The two previously
surveyed redesigns inspected below also lack a complete, private, same-witness
authentication implementation and the required security justification.

Recommend **S2-VERIFY-STATE-1**, a bounded reference model of the verifier's final
state transition, as the next separately authorised package. Its concrete boundary,
success criteria and stops are below. It would address an existing lifecycle gap;
it would not implement or demonstrate completed PQ-DAA.

This review performs source inspection, arithmetic and documentation only: **zero
guest executions, zero proofs, zero candidate installations and zero resource-limit
changes**. The cumulative ledger remains **two used, one unused**. No profile is
adopted. `PQ-DID-MITH-1`, BC-1, SPEC-001–004, all dependencies/locks, original
fixtures and historical evidence remain unchanged. Only manuscript **Sections
II–VIII** supply requirements. The PDF's SHA-256 remains
`d17ca0a20b319b88e959467cae92d91d619973f84384710ecbf960a3b850aeca`.

## What the optimisations can and cannot remove

### Existing attribution and conditional savings

The original 2^22-capped prefix spent 86.42% in the started matrix phase and 77.15%
in its 24 completed SHAKE expansions. It did not measure the later verification
phases. Corrected full-phase totals were not instrumented. It would be incorrect to
call either prefix percentage the hash share of the complete corrected guest.

The corrected isolated matrix polynomial took **113,393 cycles**, versus 142,199
previously (28,806 / 20.26% saved). The isolated forward NTT took **409,218 cycles**;
its separate twiddle preparation took **567,539 cycles**. One input-dependent
component is not a measurement of every invocation. Inspected CredValid source
performs 30 matrix expansions, 12 forward NTTs (five responses, one challenge, six
public-key polynomials), six inverse NTTs, products, hints/norm checks and hashes.
Software modular arithmetic remains substantial; its full cost is unknown.

For public preprocessing, a **component proxy** is 30 × 113,393 for matrices,
6 × 409,218 for public-key forward NTTs, 567,539 for twiddles, and the old measured
163,712-cycle key-unpack prefix: **6,588,349 cycles, 40.39% of the complete baseline**.
Subtracting that proxy leaves **9,725,125 cycles**. This is not an observed saving:
the NTT proxy used a response polynomial, matrix rejection lengths vary, public
`tr` hashing is unmeasured, and binding/parsing/paging/cache costs must be added.
No reliable maximum percentage saving for complete CredValid can be established.

The following deliberately optimistic scenarios remove **all other work**, beyond
the targeted optimisation, and retain only the indicated forward transforms at
the single observed transform cost. They ask whether even this favourable proxy
looks promising. They are **not lower bounds or predicted partitions**: transform
costs vary; perfect packing ignores reserved/page cycles; terminal po2 is unknown.

| Scenario | Retained transform proxy | Ideal capacity count at 2^17, conditional on proxy | Old per-segment model at that assumed count, including 50% |
|---|---:|---:|---:|
| A: all hashes and all other work free, except 12 forward transforms | 4,910,616 cycles | ceil(proxy / 131,072) = 38 | **7,394.884 s** |
| B: all public preprocessing and all other work free, except six private forward transforms | 2,455,308 cycles | 19 | **3,671.381 s** |
| A+B: same six private forward transforms retained | 2,455,308 cycles | 19 | **3,671.381 s** |

All inverse transforms, products, hints, parsing, holder/private hashes and paging
are omitted from these scenarios. So are A's additional proofs and B's statement
binding. The model uses `1.5 × (S×41.574386 + S×44.326462 +
(S−1)×44.748385 + 10)`; even the execution proxy is waived here. These qualified
screens still exceed 600 s and 30 s by large margins. Their overlapping benefits
must not be added. Neither establishes mathematical impossibility for a different
arithmetic implementation, smaller recursion programme or different hardware.

There is also a limit to improving proof stages while retaining 182 segments:

| Work made free at the existing partition | Remaining model, including 50% |
|---|---:|
| All base proving | **24,265.765 s** |
| All recursion, including every lift/join | **11,365.261 s** |
| Only joins | **23,466.385 s** |

Under the same rates, **three assumed po2-17 segments cost 536.253 s**, four cost
732.227 s, and one costs 144.305 s, including the original execution proxy and
allowance. Reaching three from 182 means 98.35% fewer segments. These are model
thresholds, not an assertion that either optimisation can achieve them. Even a
single measured-class base plus lift exceeds 30 s before extra obligations. No
timings for sufficiently smaller base/lift programmes establish another path.

## A — accelerated Keccak, preserving FIPS bytes

### Exact source support and required changes

The [official precompile table](https://dev.risczero.com/api/zkvm/precompiles)
links `tiny-keccak` 2.0.2, tag `tiny-keccak/v2.0.2-risczero.0`. The tag resolved at
inspection to **`8fcc866dc94dcec3e79c3b2bc8fbc51b22f2d5e1`**; all five reviewed
source files fetched by tag match their immutable-commit copies. Documentation is
a lead; no accelerated guest has been compiled or verified here.

| Required operation | Inspected implementation |
|---|---|
| SHA3-384 | `Sha3::v384()`, rate 104 bytes, suffix `0x06`, 48-byte output |
| SHAKE128 | `Shake::v128()`, rate 168 bytes, suffix `0x1f`, repeated `Xof::squeeze` |
| SHAKE256 | `Shake::v256()`, rate 136 bytes, suffix `0x1f`, repeated `Xof::squeeze` |
| Permutation | 24-round Keccak-f[1600]; sponge applies final `0x80` padding bit and little-endian state lanes |
| Cargo features | Explicit `sha3` and `shake`; default features are empty. Broader `fips202` is unnecessary for these calls; `crunchy` 0.2.2 is also required |

These conclusions come from the pinned
[SHA3](https://github.com/risc0/tiny-keccak/blob/8fcc866dc94dcec3e79c3b2bc8fbc51b22f2d5e1/src/sha3.rs),
[SHAKE](https://github.com/risc0/tiny-keccak/blob/8fcc866dc94dcec3e79c3b2bc8fbc51b22f2d5e1/src/shake.rs),
[sponge](https://github.com/risc0/tiny-keccak/blob/8fcc866dc94dcec3e79c3b2bc8fbc51b22f2d5e1/src/lib.rs)
and [permutation wrapper](https://github.com/risc0/tiny-keccak/blob/8fcc866dc94dcec3e79c3b2bc8fbc51b22f2d5e1/src/keccakf.rs).
On `target_os="zkvm"`, the **trait wrapper** calls `risc0_keccak_update`; the
exported raw `keccakf` function is still software. Native tests take the software
fallback and cannot demonstrate correct accelerator proof integration.

The current guest uses RustCrypto `sha3`, not `tiny-keccak`. A Cargo patch alone
therefore changes no calls. A reviewed adapter must replace the sponge operations,
preserve streaming state across refills, and pin a new isolated lock/build/image.
The documented opt-in is `unstable` on `risc0-zkvm` and `risc0-build`. The inspected
3.0.6 source exposes the guest symbol under the zkVM target without an additional
`unstable` gate; `risc0-build` 3.0.6's feature is empty, while the zkVM feature
forwards to platform features. This version nuance is not an integration result:
follow the documented opt-in and validate exact linking/runtime behaviour later.

Keep SDK/build **3.0.6**, platform/zkOS compatibility **2.2.3**, VM/ordinary
recursion circuits **4.0.5**, ZKP **3.0.5**, and Keccak circuit **4.0.6** when
evaluating this specific source combination. The existing host's proving feature
includes the Keccak machinery. Its special `keccak_lift_14..18.zkr.xz` programmes
and control IDs are distinct from the ordinary recursion archive; availability and
correct receipt integration are not established by that prior archive's validation.
Exact inspected local SDK paths and hashes are in the calculation input inventory.

Preserve pure FIPS 204 processing, `0 || len(ctx) || ctx || M`, the exact
`PQ-DID/credential/v1` context and application tags, all output lengths, matrix seed
`rho || column || row`, 1,026-byte matrix sampler cap and 256-byte challenge budget
(eight sign bytes plus 248 index bytes). Preserve rejected-byte consumption, lazy
refill behaviour, exhaustion rejection, canonical hint/response decoding, norms
and arithmetic. Faster unbounded or differently prefixed streams are not equivalent.

### Extra proofs and assumptions are real work

Pinned `guest/env/batcher.rs` hashes the permutation input/output states into a
SHA-256 compression transcript, calls the host permutation, and batches claims.
The raw host syscall is not a proof: the guest separately verifies an assumption
bound to the Keccak control root (or the union root for multiple batches). The
host retains input states, builds a **Keccak base proof**, checks the claim/seal,
and creates a **special Keccak lift**. Multiple batches require unions; the ordinary
VM Succinct proof must **resolve** the resulting assumption. Returning unchecked
host bytes, or accepting a conditional receipt with unresolved assumptions, fails
the intended relation. Execution-only success cannot establish this binding.

The pinned Keccak circuit accepts po2 **14–18**, defaults to **17**, charges
**200 circuit cycles per permutation**, and uses a special lift with recursion
po2 **18**. Default batch capacity is floor(2^17 / 200) = **655 permutations**.
This batch exponent is independent of the executor's segment exponent.

For the existing fixture shapes, the inspected sponge schedule gives a **static
upper scenario of 251 permutations**: 210 for all 30 matrix streams at their full
1,026-byte allowance, 5 holder SHA3, 15 public-key `tr`, 12 message `mu`, 2 challenge
sampling and 7 final challenge hashing. The calculation uses the current 457-byte
holder preimage and 1,526-byte Mcred and includes an extra permutation when this
implementation finishes squeezing an exact rate block. It is not a measured
accelerated count; changed adapter calls or schedules invalidate it.

At this default capacity the scenario needs **one Keccak base + one special lift
+ one resolve**, in addition to the VM base/lift/join work. For B batches the
source path adds B bases, B special lifts, B−1 unions and one resolution. None of
these Keccak/union/resolve times or aggregate memory peaks has been measured here.
The roughly 44 s ordinary lift/join timings must not be assigned to different
programmes solely because both use recursion po2 18. Host batching, guest SHA-256
transcripts, pages and retained buffers also cost resources. **No complete saving
percentage is supported**; the favourable retained-arithmetic scenario above
already gives little reason to spend the final proof attempt on this change alone.

### Privacy and security qualification

The [vendor security model](https://dev.risczero.com/api/security-model) qualifies
its ZK argument and notes engineering changes needed for critical privacy uses;
its cited 96/99-bit component estimates are not the project's 128-bit quantum
full-witness extraction argument. Adding a cryptographically checked coprocessor
does not close those gaps. Do not use a non-post-quantum Groth16 wrapper to claim
the same security contract.

Keccak inputs include private witness-derived states. The local prover may see
them; they must not be sent to a remote service or operational log. Inspect the
entire Keccak proof path for masking, commitment/transcript leakage and composition
with the VM proof: the reviewed circuit source does not by itself supply that
argument. No categorical claim that it is non-ZK follows merely from this inspection.
Require an unconditional final receipt and review terminal control IDs, batch/count
metadata, transcript digests and proof lengths for secret-dependent leakage. Neither
an execution timer nor native fallback tests establish complete-view simulation or
historical unlinkability. Section VIII losses cannot be imported from MITH.

**Relation versus profile:** exact constrained SHA3/SHAKE bytes could preserve the
mathematical credential relation. New guest code/image, dependencies, coprocessor
claims, verifier control parameters and proof composition change the concrete
experimental profile. They are not a BC-1 schedule-preserving change and are not
adopted in this review.

## B — independently bound public issuer-key preprocessing

### Public work that can be shared

Derive `P = DerivePublic(expected_pkI, exact_suite, algorithm_version, caps)` from
the expected, canonically decoded 1,952-byte issuer key. Public-only items are:

| Item | Derivation and possible canonical storage |
|---|---|
| Matrix A-hat | 30 bounded SHAKE128 streams from `rho || column || row`; 6×5×256 coefficients already in NTT representation; canonical unsigned residues use **30,720 bytes** |
| Scaled t1 in NTT form | Decode six t1 polynomials, multiply by 2^13 modulo q, apply the prescribed forward NTT; **6,144 bytes** |
| Twiddles | Determined by the suite alone; **1,024 bytes**, share across keys |
| `tr` | Exact SHAKE256(pkI, 64); **64 bytes** |

This compact representation totals **37,952 bytes** before version/framing/cache
overhead. The current i64 matrix alone uses 61,440 bytes; a Python object graph or
decoded guest arrays need more than the proposed packed size. Norm/hint/signature
decoding, response/challenge transforms, matrix-vector products, inverse transforms,
private `mu`/challenge hashing, holder opening, certified m/rid binding, disclosure
and non-revocation remain required. Public preprocessing does not make the issuer
signature an external unchecked predicate.

The verifier must derive P independently at key admission/cache miss using the
same bounded reference algorithms, or validate every entry against that derivation.
Cache only successful derivations. Exhaustion of the public sampler must preserve
the original rejection result; a cached implementation may not rescue an input the
bounded relation rejects. A prover's table, digest or claimed issuer signature over
a table is not by itself a proof of correct deterministic expansion.

### Two concrete binding choices, both requiring profile review

1. **Generic image with derived public auxiliary input.** Feed canonical P through
   a separately bounded public channel. The guest must use those exact values and
   commit their full canonical encoding, derivation version and original statement
   in its public journal. The verifier independently constructs P and the expected
   journal from its trusted expected key/suite and verifies that exact image/claim.
   This uses the reviewed receipt's journal binding rather than an unchecked table
   assertion. P is public, but its integrity is mandatory. The existing 16 KiB
   private-input cap cannot conceal this larger table as a private hint; introduce
   an explicit public auxiliary schema, preserving the original signed Mcred bytes.
   The existing 64 KiB public cap fits this fixture plus raw P, but worst-case framed
   admission must be checked rather than presumed. A raw journal gains roughly
   37,952 bytes plus framing, to be counted in uncached network/presentation costs.
2. **Per-issuer specialised image.** Embed independently derived P as constants,
   require the statement's issuer key/suite to match, and independently derive or
   validate the expected image from a reproducible pinned source/compiler/kernel
   recipe. Verify against that expected image, not one supplied by the prover.
   This avoids an auxiliary table in each presentation but adds per-key build/image
   registration, distribution and verification-cache work. Trusting an opaque
   third-party ELF instead would introduce an additional trusted-builder assumption.

A digest variant must first bind the verifier's expected digest to independently
derived P and then constrain the guest's actual P to that digest. Merely publishing
the prover's digest is insufficient. Hashing all 37,952 bytes with guest software
SHA3-384 would require **at least 365 permutations**, before framing: more than the
210-permutation full-cap matrix expansion scenario. Binding is not free and can
erase the gain. The exact-journal or validated-image approaches avoid that particular
application SHA3 pass, while still paying receipt/journal/image binding costs.

Cache keys include full key and suite bytes, derivation version/caps/encoding and
the expected instance association (`refI`, namespace, schema/parameters). Key
rotation starts a new immutable instance/reference; it must not rebind existing
credentials. Corruption, stale association or failed derivation rejects/recomputes
under a bounded policy. Cold verification includes derivation and cache admission;
warm verification includes lookup and integrity checks. Storage/distribution bytes,
cache misses, evictions and specialised builds must be measured separately. A
proposed 16-key cache holds at most 607,232 raw bytes with per-key twiddle duplication,
plus bounded metadata/object overhead; this is a design example, not a new limit
installed here. Public-key caching must not become a hidden-credential status query.

If P is correctly bound to the expected key, substituting its deterministic values
preserves the same mathematical acceptance predicate, including exhaustion. It does
**not** preserve the current R0 guest/image/journal interface. Nor does arbitrary
precomputation preserve the original BC-1 DAG: only existing public folding with
unchanged CGen ordering/fingerprints could do that. The empty auxiliary fields of
the current profile cannot silently acquire a table. Section VIII-A permits counting
a deterministic expansion once when actually reused; cold derivation, validation
failures and non-reused instances must still be counted. Measured cold/warm savings,
storage overhead and complete proof cost remain **unknown**.

## Two prior-survey redesigns, neither ready for adoption

The optimistic relation-preserving screens do not show a credible complete latency
path. This review therefore examines only **zkDilithium and LaZer**, using the same
two pinned candidates from the prior survey. Their reported timings are research
comparators, not predictions or acceptance measurements for PQ-DID.

### zkDilithium: a modified-signature AIR, not private FIPS verification

At commit `a9dfe21bf967fbc4319ae18b74e6e9cdb0a7482a`, the
[README](https://github.com/guruvamsi-policharla/zkdilithium/blob/a9dfe21bf967fbc4319ae18b74e6e9cdb0a7482a/README.md)
describes knowledge of a signature on a **public message**, with research code not
independently reviewed for production. The inspected `starkpf` code supplies
polynomial constraints, trace generation, a Poseidon challenge and Winterfell proof
plumbing. Its concrete modulus is **7,340,033**, K=4, N=256, with generated key/matrix
constants; these are not the ML-DSA-65 parameters. The public input is a 12-element
message digest. Its `Serializable::write_into` body is empty while boundary
assertions use the message: **public-input transcript binding needs audit**, not a
claim here of a demonstrated exploit. See the pinned
[AIR](https://github.com/guruvamsi-policharla/zkdilithium/blob/a9dfe21bf967fbc4319ae18b74e6e9cdb0a7482a/src/starkpf/air.rs)
and [parameters/trace code](https://github.com/guruvamsi-policharla/zkdilithium/blob/a9dfe21bf967fbc4319ae18b74e6e9cdb0a7482a/src/starkpf/mod.rs).

The [paper, §§3.4–4](https://eprint.iacr.org/2023/414.pdf) changes the signature's
hash, public-key compression/hints and challenge sampling; its measured zk-20
variant changes the modulus. It explicitly says the implementation is **not ZK**.
Across its benchmark variants it reports 304–4,822 ms proving, 19.8–31.4 ms verifying,
19–235 MB prover memory and 85.6–173.3 KB transcripts, at 115 conjectured bits, on
a single-thread 2019 MacBook Pro i9. These results are for the paper's altered
relation and security assumptions, not private ML-DSA-65 or this machine. There is
no measured saving for adding ZK or full authentication.

A possible architecture is **one joint AIR** with private signature and Mcred,
canonical 1,024-byte attributes, holder SHA3-384 opening, certified rid, projection
of the same attributes and the same rid's depth-20 SHA3 path, bound to expected
public context/state. The available AIR does not implement this. Adding exact
SHA3 and private parsing/path constraints may reintroduce large costs; changing
those primitives instead changes the protocol. Separate signature, holder and
path proofs without extractable equality of their witnesses are unacceptable.

Before even treating this as a reproducible candidate, pin its Winterfell `f23`
branch dependency (the repository has no Cargo.lock), resolve its older Python
tooling requirements, implement/audit masking and transcript binding, parameterise
expected issuer keys, and justify joint quantum extraction/simulation. No trusted
setup is apparent in the STARK design, but hash/FRI parameters and conjectured
security are not the manuscript's losses. Its modified signature must have a new
name/suite; it must **never be labelled FIPS ML-DSA-65**. No defensible complete
cost estimate, resource bound or application-target claim is available.

### LaZer: lattice anonymous-credential showing, not the current credential

The inspected commit is **`fc455c3b48bfe9e4b1e0607c74ae676c04020923`**. Its
[anonymous-credential example](https://github.com/lazer-crypto/lazer/blob/fc455c3b48bfe9e4b1e0607c74ae676c04020923/python/anon_cred/anon_cred.py)
implements a lattice linear-relation ZK showing with binary/norm constraints:

```text
AR*r + ATAU*tau - B1*s1 - B2*s2 + AM_private*m_private + AM_public*m_public = 0
```

It uses a Falcon preimage sampler during blind issuance. The example ring has
degree 64, q=12,289; AR is 8×16, AM is 8×8, and showing uses an 8×48 matrix with
bounded/binary witness blocks. Its message is **64 bytes** with disclosure at
selected polynomial blocks. The [showing parameters](https://github.com/lazer-crypto/lazer/blob/fc455c3b48bfe9e4b1e0607c74ae676c04020923/python/anon_cred/anon_cred_p2_params.py)
are not a drop-in parameterisation of the 1,024-byte schema, holder hash or
ML-DSA-65 verification. Reusable code includes linear proof machinery, bound checks,
public/private block separation and an issuance/showing skeleton.

The [paper's anonymous-credential comparison](https://eprint.iacr.org/2024/1846.pdf)
reports approximately **0.198 s showing, 0.117 s issuance and 29 KB credential
size**, using its lattice credential construction and hardware. These are not the
bytes or time of complete PQ-DID authentication. The paper's MLWE/Mod-ISIS-style
assumptions and proof analysis need to be matched to the selected protocol and
quantum adversary model. Its reproduction revision
`10eafeca4cd53ff4fc54193dce904dbd0026fefd` differs from the inspected current tree.
Neither those timings nor separate aggregation benchmarks establish a saving for
the required joint relation.

The current [README](https://github.com/lazer-crypto/lazer/blob/fc455c3b48bfe9e4b1e0607c74ae676c04020923/README.md)
requires Linux x86-64 with AVX-512/AES, GCC ≥13.2, CMake ≥3.26, Sage ≥10.2 and
Python/CFFI tooling. The recorded WSL CPU exposes AVX2/AES but **not AVX-512F/BW/VL**;
no supported build of this pinned configuration is established here. Portability
of earlier/narrower linear paths remains untested. No install or benchmark ran.

A joint construction would have to certify the issuer-approved vector and holder
binding, then prove the *same* xH/m/rid in signature showing, SHA3 opening,
schema/disclosure and the private zero-leaf Merkle path. The linear example does not
encode SHA3 or those path constraints. A mixed nonlinear proof system would need
binding commitments and extractable equality across every component, with a
composed privacy argument; otherwise a prover could combine different credentials
or identifiers. Replacing the revocation hash/tree with a lattice-friendly design
would instead require a new revocation/history construction and security review.
Blind issuance also changes what the issuer approves/sees; it cannot silently
replace the existing direct certification semantics. Full-key/parameter trust,
sampler bounds, 64→1,024-byte growth, leakage and historical unlinkability remain
unresolved. No measured complete cost or credible bounded implementation route
currently closes these gaps.
